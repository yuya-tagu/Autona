# Autona ドキュメント基盤

このディレクトリは、**既に実運用されている Autona** を壊さずに今後の変更
（Companion / Stream Deck 連携、外部制御 API、OBS 連携拡張など）を安全に進める
ための運用・設計ドキュメント置き場です。

## このディレクトリの目的

- 既存の**仕様・運用制約・変更影響・実装タスク**をリポジトリ内に蓄積する
- **調査・設計と実装を分担しても引き継げる**情報源にする
  （タスクの種類に応じて担当・実施環境を割り当てる）
- 「動いているものを壊さない」ための、変更前チェックの拠り所にする

## ディレクトリ構成

| ディレクトリ | 役割 |
|-------------|------|
| [`product/`](product/) | 既存機能・画面・ユーザー操作・利用シナリオ・業務フロー |
| [`architecture/`](architecture/) | 現在のアーキテクチャ・主要モジュール・責務分離・データ/状態の流れ・外部連携 |
| [`operations/`](operations/) | 実運用手順・配信時の起動順・障害対応・復旧手順・壊してはいけない操作 |
| [`decisions/`](decisions/) | ADR 形式の意思決定ログ（なぜその設計/制約にしたか） |
| [`changes/`](changes/) | 変更提案・影響範囲・移行方針・互換性・リリース時の注意点 |
| [`tasks/`](tasks/) | 担当者に渡す調査タスク・実装計画・実装チケット |

## 運用フロー

変更（新機能・連携追加など）は、原則として次の流れで進める。
各タスクは種類に応じて担当・実施環境を割り当てる。

```
1. 調査       → tasks/investigate-*.md を実施し、コードの実態・不明点を確定する
2. 影響分析   → changes/*-impact-analysis.md に既存運用への影響を整理する
3. 意思決定   → decisions/ADR-NNN.md で採否・理由・不採用案・見直し条件を記録する
4. 実装タスク化 → tasks/implement-*.md を自己完結したチケットとして起こす
5. 実装       → チケットを消化（実装・検証・PR）する
6. ドキュメント更新 → 確定した事実を docs/ に反映。仕様が変わったら
                     .claude/design/Design.md（正本）も更新する
```

補足:

- **ステップは前後しうる**が、`decisions/` の前に「調査」と「影響分析」を置くことで、
  事実不足のまま設計を確定するのを避ける。
- `tasks/` は**調査タスク（investigate-*）と実装タスク（implement-*）の両方**を持つ。
  決定前は investigate-*、決定後は implement-*。
- **ドキュメント更新は1回のステップではなく各段階で随時**行う。特に実装後に
  `product/` `architecture/` `operations/` を実態へ追従させる。
- 役割を混ぜない: 「なぜ（decisions）」「何に響くか（changes）」「どう作るか（tasks）」を分離する。

## 他ドキュメントとの関係

このディレクトリは**運用・変更管理の視点**を担う。実装の正本は別にある。

| ドキュメント | 役割 | 正本 / 参照 |
|-------------|------|------------|
| [`../CLAUDE.md`](../CLAUDE.md) | 開発原則・Git 方針の要点・アーキ概要・参照マップ（詳細索引は [`../.claude/README.md`](../.claude/README.md)） | 開発運用の正本 |
| [`../.claude/design/Design.md`](../.claude/design/Design.md) | UI 実装方式・データモデル・画面仕様・デザインシステム・ホットキー | **実装仕様の正本** |
| [`../.claude/architecture/`](../.claude/architecture/) | コードベース調査の事実情報（import 関係・状態キーパス等） | 調査ログ |
| [`../FEATURES.md`](../FEATURES.md) | 機能一覧（リバースエンジニアリング） | 参考（※後述の注意） |
| [`../ROADMAP.md`](../ROADMAP.md) | 将来機能の提案（PdM） | 参考 |
| [`positioning.md`](positioning.md) | タグライン・ポジショニング・差別化・メッセージング規則 | **対外メッセージングの正本** |
| `docs/`（本ディレクトリ） | 運用制約・変更影響・調査/実装タスク | 運用・変更管理の視点 |

矛盾があった場合の優先順位: **コードの実態 > `.claude/design/Design.md` > `CLAUDE.md` > その他 Markdown**。
`docs/` 配下に書く内容が実装仕様に踏み込む場合は、Design.md を正本として参照し、
ここには「運用・変更時に注意すべき点」を書く。

> ⚠️ **既知の不整合（2026-06-14 時点）**: ルートの `FEATURES.md` と `AGENTS.md` には
> ステージストライク機能（`/stage-strike-app`・`StageStrikePage`・`stage_strike` 状態等）の
> 記述が残っているが、`CLAUDE.md` には「削除済み」と明記されており、コードベース上にも
> 該当ファイル・ルートは存在しない（確認済み）。`docs/` 配下では**ステージストライクは
> 現行ビルドに存在しない**前提で記述する。詳細は [product/current-features.md](product/current-features.md) を参照。

## 記入ルール

- **確認できない既存仕様は推測で書かず `TBD` とする。** 確認方法（読むべきファイル/手順）を併記する
- 既存アプリケーションコードの変更はこのドキュメント作業では行わない
- 相対日付は絶対日付に変換して書く（例: 「来週」→ `2026-06-21`）
- 既存ドキュメント（`CLAUDE.md`・`.claude/`）と重複させず、相互リンクで参照する
