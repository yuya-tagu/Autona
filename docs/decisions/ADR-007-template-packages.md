# ADR-007: テンプレートパッケージ（リザルト画像・サムネイルのデザインを配布物にする）

## Status

Accepted（2026-11-17 オーナー承認。末尾の論点は 1 = A・2 = B・3 = A）

## Context

TOP8 リザルト画像と試合サムネイルのデザインを、第三者が作って配れるものにしたい（MIT で公開するので、
他の技術者・デザイナーが自作のデザインを紹介できるようにする）。

**次の方針は採用済みで、この ADR では覆さない。**

- 配布の単位は**テンプレートパッケージ**（HTML / CSS / JS と画像のフォルダ）。実行ファイル（ワーカー）にはしない
- 描画は Autona 本体に残す（別プロセスのワーカーに出さない）
- 第三者の実行ファイルを Autona が起動する汎用のワーカー登録は作らない。機能を足したい技術者の入口は
  v1 API を叩く外部ツール（ADR-001 の境界）

**2026-11-17 に調べて分かった事実（判断の根拠）:**

| 項目 | 事実 |
|------|------|
| 描画の仕組み | リザルトもサムネイルも `src/AutonaOffscreenRenderer.py`（QWebEngineView のオフスクリーン描画）のサブクラス。`layout/<フォルダ>/result.html`（`thumbnail.html`）を **file://** で読み、`initResult(payload)`（`initThumbnail`）を呼んで撮る。デスクトップ専用（ヘッドレスは 503） |
| レイアウトの一覧 | **コードに固定**。リザルトは `ResultService.py` の `LAYOUT_SUBDIRS` / `LAYOUT_SIZES` / `LAYOUT_NAMES`（6 種）と `TEAM_LAYOUTS`、サムネイルは `ThumbnailService.TEMPLATE_IDS`（`type_a` / `type_b`）と `ThumbnailRenderer.TEMPLATE_SUBDIRS`。足すには Python・`CoreWords`・i18n の編集が要る（Design.md §7.3 / §7.4） |
| サムネイルの型の設定 | 配置の数値は `assets/thumbnail_base/thumbnail_types/type_*.json`（パッケージの外）。既定の背景も `./assets/...` を指す |
| 共有の依存 | 同梱テンプレートは `../include/`（jquery・lodash ほか）を読み、リザルトは `../thumbnail/thumbnail_assets.js`（別のテンプレートのフォルダ）も読む |
| 既存の発見の仕組み | `core/LayoutCatalog.py` が `layout/*/settings.json` の `autona` ブロック（`kind`: scoreboard / commentary / top8）かフォルダ名の規約でデザインを見つける。**result / thumbnail は kind に無い** |
| 描画の権限 | file:// の文書として動く。`QTWEBENGINE_DISABLE_SANDBOX=1`。サムネイルのビューは `LocalContentCanAccessFileUrls` / `LocalContentCanAccessRemoteUrls` が True。**テンプレートの JS はこの PC の任意のファイルを読めて、外部へ送れる** |
| 既存の隔離の仕組み | プレビュー用のリスナー（ADR-005 SF-8a。別ポート = 別オリジン）。出すのは `layout/`・`assets/`・`user_data/` の画像・`out/program_state.json`・v1 の READ だけで、書き込みはトークンがあっても断る |
| 既存の取り込みの検査 | `core/AssetPackService.py`（ゲームアセット）。zip の中央ディレクトリの事前検査・全エントリの検査（パス・リンク・件数・展開後の大きさ・空き容量）・作業フォルダで組んでから置き換え・退避と復帰・アップロードの枠。ルートは SHELL |
| 共有の入口 | Issue テンプレート「layout 投稿」（種類に thumbnail / result、MIT での公開に同意のチェック）と `CONTRIBUTING.md`。アプリに取り込む機能は無い |
| ライセンス | `layout/include/gsap.min.js` は MIT ではない（GSAP の "No Charge" License。再配布に条件）。フォントは `FONT-LICENSES.txt` |
| ROADMAP | 3-3-3「レイアウト・テンプレート共有」（GitHub の URL から `layout/` のパッケージを取り込む・サムネイルテンプレートの自作 UI）。設計はまだ無い |

**問題は 2 つ。** (1) デザインはファイルとして配れる形なのに、一覧が固定なので置いても使えない。
(2) 今の描画の権限のまま第三者のテンプレートを勧めると、テンプレートの JS がこの PC のファイルを読んで外へ出せる。

## Decision

### D1: 単位は「`layout/` 直下の 1 フォルダ」。マニフェストは `settings.json` の `autona` ブロック

- テンプレートパッケージ = `layout/<フォルダ名>/` の 1 フォルダ。中身は入口の HTML・CSS・JS・画像・フォントと `settings.json`
- `core/LayoutCatalog` の `kind` に **`result` と `thumbnail`** を足す（既存の scoreboard / commentary / top8 と同じ読み手・同じ壊れたブロックの扱い）

```json
{
  "autona": {
    "kind": "result",
    "contract": 1,
    "displayName": {"ja": "横型 TOP8", "en": "Horizontal TOP 8"},
    "entry": "result.html",
    "size": [1920, 1080],
    "rows": "players",
    "author": "taguyan",
    "license": "MIT"
  }
}
```

| キー | 必須 | 内容 |
|---|---|---|
| `kind` | ○ | `result` / `thumbnail` |
| `contract` | ○ | テンプレートの契約の番号（D3）。Autona が知らない番号のパッケージは一覧に出さず警告する |
| `displayName` | | 文字列か `{ja, en}`。省略時はフォルダ名から作る（既存の規則） |
| `entry` | | 入口の HTML（フォルダ内のファイル名だけ）。省略時は `result.html` / `thumbnail.html` |
| `size` | ○ | 出力の `[幅, 高さ]`（px。上限を設ける） |
| `rows` | result で ○ | `players`（単独。16 行まで渡る）/ `teams`（団体。8 行）。今の `TEAM_LAYOUTS` の代わり |
| `template` | thumbnail で ○ | 配置の設定の JSON（フォルダ内のファイル名だけ）。今の `type_*.json` をパッケージの中へ移す |
| `author` / `license` | | 一覧と取り込みの確認に表示する。第三者のパッケージでは `license` を必須にする（D5） |

- フォルダ名へのフォールバックは作らない（result / thumbnail は必ずブロックで宣言する。同梱の 8 フォルダにブロックを足す）
- **id**: 同梱の 8 種は今の id を変えない（`horizontal` / `horizontal_16` / `vertical` / `vertical_geki` / `team` / `team_split` /
  `type_a` / `type_b`。`settings.json` の保存値・state の `result_layout`・v1 の値・`thumbnail_config` が使っている）。
  id → フォルダの対応は core に凍結した表で持つ。**それ以外のパッケージの id はフォルダ名**。フォルダ名が同梱の id と同じなら
  同梱を勝たせ、そのフォルダは一覧に出さず警告する。保存データの移行は要らない
- 同梱の表示名は今までどおり `CoreWords`（ja / en）。第三者のパッケージは `displayName`
- `ResultService` / `ThumbnailService` と 2 つのレンダラーは、固定の表ではなくカタログを読む。保存された id のパッケージが
  無くなっていたら既定（`horizontal` / `team` / `type_a`）で描く（今の `_resolve_template_id` と同じ倒し方）
- 一覧は `GET /api/v1/layouts`（kind の追加だけ）。リザルトとサムネイルのページは固定の選択肢をやめてこれを読む
  - T1 の実装: テンプレートの kind でも `displayName` はほかの kind と同じく文字列（プログラムの言語）のまま保ち、
    両言語は足したキー `displayNames`（`{ja, en}`）で出す。ページは `displayNames` を UI の言語で表示する
  - T1 の実装: 一覧の場所は `LayoutCatalog.Root()` の 1 つ（アプリのディレクトリの `layout/`。`bootstrap_core()` が渡す）。
    サービス・レンダラー・ルートが別々にフォルダを組まない

### D2: 共有の部品は `layout/include/` に置き、パッケージはそれを参照するだけにする

- パッケージが自分のフォルダの外で読んでよいのは `../include/` だけ。`../thumbnail/thumbnail_assets.js` は `include/` へ移す
  （同梱のリザルトが別のテンプレートのフォルダに依存しているのを解く）
  - T1 の実装: 同梱のリザルト 4 種が共有していた `result/result.js`・`result/result.css`・`result_team/result.css` も同じ理由で
    `include/` へ移した（`include/result.js`・`include/result.css`・`include/result_team.css`）。同梱のこれらの CSS をその場で
    書き換えていた利用者は、更新後に変更が効かなくなる（リリースノートで案内する）
- `include/` のファイルをパッケージに同梱させない（特に `gsap.min.js`。再配布の条件を配布者に負わせない）。
  `include/` に無いライブラリ・フォントを使うなら、パッケージの中に入れてライセンスの文書も入れる（配布者の責任）
- サムネイルの `template` の JSON が指す画像（既定の背景など）は、パッケージの中か `assets/` の相対パスだけを受ける

### D3: テンプレートの契約（contract 1）を外部契約として固定する

- 入口のページは `initResult(payload)`（thumbnail は `initThumbnail(payload)`）を定義し、描き終えたら今の同梱テンプレートと同じ
  合図（`RENDER_READY`）を出す。撮るタイミング（`RENDER_PAINTED`）はレンダラー側の仕事のまま
- `payload` は今の `ResultService.BuildPayload()` / `ThumbnailService.RenderPayload()` の形。golden
  （`tests/fixtures/result/golden.json` / `tests/fixtures/thumbnail/golden.json`）が契約の写しになる。
  **以後はキーの追加だけ**（改名・削除・意味の変更は `contract` を上げる）
  - T1 の実装: リザルトの payload に `data.rows`（マニフェストの `rows`: `players` / `teams`）を足した。同梱の `include/result.js` は
    団体かどうかをこの値で決める（id の接頭辞 `team` で決めると第三者の id では判定できない。`rows` の無い payload のときだけ
    接頭辞を見る）
- payload の中のパスは「描画の文書から読める URL」で渡す（D4 で file のパスから変わる。変え方も契約に書く）
- 契約は文書にする（T4。作り方・最小のサンプル・ローカルでの確かめ方）

### D4: 描画はプレビュー用のリスナーのオリジンで行い、ほかへの要求を止める【論点 3】

第三者のテンプレートを取り込めるようにする**前に**、描画の権限を絞る（D6 の順）。

- レンダラーは `http://127.0.0.1:<previewPort>/layout/<フォルダ>/<entry>` を読む（file:// をやめる）。
  そのオリジンから読めるのは、プレビュー用のリスナーが出すもの（`layout/`・`assets/`・`user_data/` の画像・v1 の READ）だけ。
  この PC のほかのファイルは読めず、本体への書き込みもできない（SF-8a の判定をそのまま使う。新しい表は作らない）
- ビューの設定: `LocalContentCanAccessFileUrls` / `LocalContentCanAccessRemoteUrls` は False。権限の要求は全部 deny。
  新しいウィンドウは作らない。メインフレームの遷移は読み込んだ文書だけ
- **要求の遮断**: ビューのページに要求のインターセプタを付け、プレビューのオリジン（と `data:` / `blob:`）以外への要求を止める
  （外部への送信・`file:`・本体のポート）。インターセプタはページに付ける（プロファイルに付けない。共有ビュー・Designer と
  同じ既定プロファイルのため。`_ShellRequestInterceptor` と同じ理由）
- payload のパス（キャラの絵・背景・アイコン・スポンサーロゴ）は、プレビューのオリジンから読める URL に組み直す。
  **プレビューが出していない場所を指すもの**（実装前に棚卸しする。分かっている候補: アーカイブ切り抜きの `_bg.jpg`
  （ジョブフォルダ）・`./tmp/` の下・絶対パス）は、描画 1 回ぶんだけ読める枠を core に置いて id で渡す
  （テンプレートにパスを渡さない。`AssetPackService` のフォルダ選択の枠と同じ考え方）
- プレビューのポートが無いとき（bind 失敗・Web サーバーの起動前）は描画を断る（`result_render` / `thumbnail.render` の
  `error` に固定のコード）。**file:// に代えない**
- 同梱の 8 種について、file:// と新しい経路の出力が同じ画素になることを確かめる（フォント・画像の decode・背景の透過）
- `QTWEBENGINE_DISABLE_SANDBOX=1` はプロセス全体の設定で、置いた理由が記録に無い。この段階で理由を調べ、外せるなら外す。
  外せないなら理由を Design.md に書いて残す

### D5: 取り込みは zip のアップロード。検査は `AssetPackService` と共有する【論点 2】

- **対象は全 kind**（論点 2 = B）: `result` / `thumbnail` に加えて `scoreboard` / `commentary` / `top8`（OBS のオーバーレイ）も
  同じ入口で入れられる。`designer` は宣言できないまま（`layout/custom/` 専用）
- 入口は各ページのデザイン一覧の「追加」（リザルト / サムネイル / BOARD / 実況 / TOP 8）。どのページから入れても、
  置き場所と kind は zip のマニフェストが決める。zip を 1 つ受け、検査してから `layout/<フォルダ名>/` に置く
- **隔離の差を確認に出す**: `result` / `thumbnail` は D4 の隔離の中で描く。OBS のオーバーレイは本体と同じオリジンで動き
  （THIS_PC の読み取りに届く。`external-control-api.md` の前提のまま）、OBS のブラウザソースの中では外部への通信も止められない。
  取り込みの確認は kind で文を分け、オーバーレイでは「このデザインのスクリプトは配信 PC の Autona の情報を読めて、外部と通信できる」
  ことを明示する。手で置く今の経路と権限は同じで、増えるのは入れやすさ
- zip の検査（中央ディレクトリの事前検査・全エントリのパス / リンク / 件数 / 展開後の大きさ・空き容量・作業フォルダで組んでから
  置き換え・退避）は `AssetPackService` の実装を core の共通の部品に切り出して両方が使う（写しを作らない）
- テンプレート固有の検査:
  - トップは 1 フォルダで、その直下に `settings.json`。`autona` ブロックが必須（フォルダ名の規約へのフォールバックは、
    手で置いた既存のフォルダのためだけに残す）。`kind` は `designer` 以外の知っている値、`license` がある、
    `entry` がフォルダの中にある。`result` / `thumbnail` は加えて `contract` が知っている番号で、`template` がフォルダの中にある
  - 拡張子は許可リスト（html / css / js / json / 画像 / フォント / txt / md）。実行ファイル・スクリプトのほかの形式は断る
  - 展開後の大きさと件数に、ゲームアセットより小さい上限を置く
  - フォルダ名は安全な文字だけ。同梱のフォルダ名・`include` / `custom` / `designer_runtime` / `icons` は断る。
    既にある第三者のフォルダは上書きの確認を取る
- 取り込みの前に、作者・ライセンス・「このテンプレートはスクリプトを含む。信頼できる配布元のものだけを入れる」を出して確認を取る
- 削除もページからできる（同梱は消せない）。使っている最中のテンプレートを消したら既定に戻る（D1）
- ルートはアップロード・取り込み・削除とも SHELL（`layout/` に置いたものは OBS のオーバーレイと同じオリジンで出るので、
  同じオリジンのレイアウトのスクリプトから操作させない）。v1 の拒否は `reason` 付き（ゲームアセットと同じ形）
- **URL やレジストリからの取得は作らない**（この ADR の範囲外。まず zip）

### D6: 段階分け（1 段階 = 1 PR）【論点 1】

依頼の順は「発見 → 取り込み → 描画経路の安全化」だったが、**安全化を取り込みより先にする**（論点 1 = A）。
取り込みを先に出すと、「zip を入れるだけで、この PC のファイルを読めるスクリプトが動く」期間ができるため。
手でフォルダを置く経路（T1）は今と同じ信頼の前提（自分で置いたもの）なので、先に出してよい。

| 段階 | 内容 | 検証 | 区分 |
|------|------|------|------|
| **T1 発見** | `LayoutCatalog` の kind `result` / `thumbnail`、同梱 8 種にマニフェスト、id の凍結した表、`type_*.json` をパッケージの中へ、`thumbnail_assets.js` を `include/` へ、`ResultService` / `ThumbnailService` / レンダラーがカタログを読む、ページの選択肢を `GET /layouts` から、`layout/` に手で置いたパッケージが一覧に出て描ける、Design.md §7.3 / §7.4 と `layout/README.md` の更新 | pytest: カタログ（壊れたブロック・知らない `contract`・id の衝突）、payload の golden が変わらないこと、保存済みの id がそのまま読めること、無くなったテンプレートは既定で描くこと。Web: ページの jest。実機: 隔離データで同梱 8 種の出力が変わらないこと、手で置いた試作のパッケージが描けること | 通常 |
| **T2 描画経路の安全化** | D4 の全部（プレビューのオリジンでの読み込み・ビューの設定・要求の遮断・payload のパスの棚卸しと組み直し・描画 1 回ぶんの枠・ポートが無いときの拒否・sandbox の設定の調査） | pytest（実 QtWebEngine）: テンプレートから `file:`・外部・本体のポートへの要求が届かないこと、プレビューが出すものは読めること、ポートが無いと断ること。同梱 8 種の画素の比較。アーカイブ切り抜きのサムネイル（`_bg.jpg`）と SCORE の X 投稿（同期の描画）が今までどおり描けること。実機: 3 経路（リザルト・サムネイル・アーカイブ）で生成 | **高** |
| **T3 取り込み** | D5 の全部（zip の検査の共通化・テンプレート固有の検査・アップロードの枠・取り込みと削除の v1（SHELL）・5 つのページの「追加」と kind ごとの確認・作者とライセンスの表示） | pytest: 検査の表（パスの抜け・リンク・拡張子・大きさ・マニフェストの不備・`designer` の拒否・フォルダ名）を kind ごとに、置き換えの途中の失敗からの復帰、使用中のデザインを消したときの倒し方、ルート台帳とアクセス区分。E2E: 取り込んでから一覧に出て描くまで（result と scoreboard）。実機: 試作のパッケージの zip を入れて生成・OBS のブラウザソースで表示・削除 | 高（`layout/` への書き込み） |
| **T4 配布の案内** | テンプレートの作り方の文書（契約 1・最小のサンプル・zip の作り方・ライセンスと `include/` の規則）、README の「コミュニティのテンプレート」の一覧、Issue テンプレートと `CONTRIBUTING.md` の更新、ROADMAP 3-3-3 の書き直し | 文書のとおりにサンプルを作って取り込めること | 軽微 |

- T1 だけでも「フォルダを置けば使える」ようになる。T2 が入るまで、第三者のテンプレートを README では勧めない
- T2 は第三者のテンプレートが無くても価値がある（同梱テンプレートの読み込みを、今ある隔離の仕組みに揃える）

## Alternatives considered

- **描画を別プロセスのワーカーにする**（ADR-006 の形）: Chromium をもう 1 つ配ることになり、ワーカーに分ける動機
  （重い依存・解析の負荷・更新の周期）がどれも当てはまらない。デザインを作る人が書くのは HTML / CSS で、実行ファイルではない。不採用
- **第三者の実行ファイルを登録できる汎用のワーカー機構**: 任意の exe を Autona が起動することになり、ワーカーごとに
  ページも要るので、実質プラグイン機構になる。入口は v1 API の外部ツールで足りる。不採用（2 つ目の実ワーカーが出たら見直す）
- **描画用の独自スキーム（`QWebEngineUrlSchemeHandler`）で読む**: Web サーバーに依存せず、渡すファイルを 1 つずつ決められる。
  しかしスキームの登録は QApplication の生成より前に要り、起動の順（`main.py` / `bootstrap.py`）に手が入る。
  プレビュー用のリスナーは同じ隔離をすでに持ち、テストもある。不採用（ヘッドレスで描く話が出たら見直す）
- **file:// のまま、設定だけ絞る**（`LocalContentCanAccess*` を False）: file:// の文書どうしの扱いは Chromium の設定に頼り、
  「読めるのはこのフォルダだけ」を言い切れない。不採用
- **JS を禁止し、HTML / CSS だけのテンプレートにする**: 安全だが、今の同梱テンプレートは JS で payload を DOM にしている。
  宣言的なテンプレート言語を新しく作ることになる。不採用
- **Designer（レイヤー型）をリザルト / サムネイルにも広げる**: コードを書かない人が作れるが、別の大きな機能
  （ROADMAP「サムネイルテンプレートの自作 UI」）。この ADR の配布の仕組みの上に後から載せられる。範囲外
- **取り込みを `result` / `thumbnail` だけにする**: 隔離して描くものだけを zip で入れられるようにする案（起案時の推奨）。
  OBS のオーバーレイは隔離が無いので外していたが、配布の入口を 1 つにすることを優先し、確認の文で差を示す形にした。不採用（論点 2 = B）

## Consequences

**良い影響:**

- デザインを Python の編集なしに足せる。第三者が作ったものを zip 1 つで入れられる
- 同梱のテンプレートも含め、描画がこの PC のファイルと外部に届かなくなる
- zip の検査が 1 か所になる（ゲームアセットとテンプレート）
- ROADMAP 3-3-3 の最初の一歩になる（URL からの取得は、この取り込みの前段に足せる）

**受け入れるリスク・コスト:**

- 描画がプレビュー用のリスナーに依存する。bind に失敗した起動では画像を作れない（今は作れる）
- テンプレートから外部の CDN（Web フォント・ライブラリ）を読めなくなる。要るものはパッケージに入れる（論点 3）
- payload の形とテンプレートの契約が外部契約になり、変えにくくなる（追加だけ）
- T2 は 3 つの描画の入口（リザルト・サムネイル・アーカイブ切り抜き）と同期の描画（SCORE の X 投稿）に触れる。区分は「高」
- 第三者のテンプレートの JS は、隔離した後もプレビューが出すもの（選手名を含む state・v1 の READ）を読める。
  外へ送る経路は止めるが、描いた画像の中身はテンプレートが決める。「信頼できる配布元のものだけ」の確認は残す
- OBS のオーバーレイを zip で入れやすくなる。権限は手で置くのと同じ（本体と同じオリジン・外部と通信できる）だが、
  入れる人が増える。守りは取り込みの確認の文と、秘密・構成の変更を SHELL に分けてある既存の区分だけ
- `include/` に無い部品を各パッケージが持つので、パッケージごとにライブラリの版がばらつく

## Revisit conditions

- ヘッドレスでリザルト / サムネイルを描く要望が出たら、D4 の読み込み方（独自スキーム・別プロセスの描画）を見直す
- WebView2 への移行（ADR-005 の Revisit）を決めたら、D4 を見直す（オフスクリーン描画の持ち方が変わる）
- 第三者のテンプレートが増え、zip の受け渡しが手間になったら、URL / 一覧からの取得（ROADMAP 3-3-3）を別の ADR にする
- 取り込んだ OBS のオーバーレイが問題を起こしたら（情報の持ち出しなど）、オーバーレイの取り込みを止めるか、
  第三者のオーバーレイを別オリジン（プレビュー用のリスナーと同じ形）で出す案を別の ADR で検討する
- 2 つ目の実ワーカーが出てきたら、ワーカーの発見と登録の一般化を別の ADR で検討する

## オーナーの判断が要った論点（2026-11-17 決定: 1 = A・2 = B・3 = A）

1. **段階の順**（D6）
   - **A（推奨・採用）: 発見 → 描画経路の安全化 → 取り込み**。zip で入れられるようになる時点で、テンプレートは隔離されている。
     取り込みが使えるようになるのは 1 段階遅れる
   - B: 発見 → 取り込み → 安全化（依頼の順）。配布は早く始められるが、安全化が入るまで、入れた zip のスクリプトが
     この PC のファイルを読める
2. **取り込みの対象**（D5）
   - A（推奨）: `result` / `thumbnail` だけ。隔離して描くものだけを zip で入れられるようにする。OBS のオーバーレイは
     今までどおり手で置く
   - **B（採用）: 全 kind**。配布の入口は 1 つになるが、OBS のオーバーレイは本体と同じオリジンで動くので、zip で気軽に入れられると
     今より危険が増える
3. **テンプレートからの外部への通信**（D4）
   - **A（推奨・採用）: 全部止める**。描画はオフラインで完結し、選手名などを外へ送る経路が無い。Web フォントやライブラリは
     パッケージに入れてもらう
   - B: 止めない。CDN のフォントなどをそのまま使えるが、テンプレートが読んだものを外へ送れる
