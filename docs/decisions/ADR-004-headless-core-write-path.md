# ADR-004: 書き込み経路アーキテクチャ（Headless Core / Actions 層への集約）

## Status

Accepted（2026-08-28 PdM 承認。PdM 方針指示「Qt ウィジェットが書き込み経路の主役という設計を根本から見直し、軽く、他アプリに影響を及ぼさない堅牢なアプリケーションを目指す」を受けた具体化。
併せて **移行専念**（機能開発と交互ではなく、移行を連続実施して新旧経路の併存期間を最小化する）を PdM が決定）

> 設計詳細・移行ステップ・検証方法は
> [../changes/headless-core-redesign.md](../changes/headless-core-redesign.md) を正とする。
> 本 ADR は「なぜこの方針か」の記録のみを持つ。

## Context

2026-08-28 の全体調査（src/ 34,199 行・web/ 12,108 行・tests/ 9,401 行）で、
現行の書き込み経路について以下の事実を確認した:

- `StateManager.Set` の呼び出しは **21 ファイル・約 197 箇所**に散在し、その最大の書き手は
  Qt ウィジェット（`AutonaScoreboardWidget` 43、`AutonaCrewBattleWidget` 31 ほか）
- 入力ウィジェットの `objectName()` がそのまま state キーパスになる動的バインディングが
  支配的パターンで、**ウィジェット構造が state スキーマの正本**になっている
  （known-smells S-14。マイグレーション層なし、契約テストで凍結中）
- `AutonaWebServerActions`（47 メソッド）は Design.md R-Sync-1 で「書き込みの単一経路」と
  位置づけられているが、実態は **StateManager に一度も書かない「Qt ウィジェットへのリモコン」**
  （`GetScoreboard(...)` 49 回、シグナル emit / メソッド呼び出し / `findChild`+`setValue` の 3 系統）。
  ドメインロジックの実体はすべてウィジェット側にある
- グローバルホットキー 9 本は Actions を迂回してウィジェットのバウンドメソッドに直結しており、
  **Qt UI / REST(v1) / REST(legacy)+Socket.IO / ホットキーの 4 系統の書き込み経路**が併存する
- 「パネル未構築だと書き込み・ホットキーが無言で死ぬ」クラスのバグが実際に発生している
  （`Autona.py` の Ctrl+Shift+P 事例、テスト戦略の過去バグ分類でも「UI⇄StateManager 同期漏れ」が
  40 件中 12 件で最多）
- PySide6 のネイティブクラッシュ地雷（agent-pitfalls #9〜#15）は、ドメインロジックが
  Qt オブジェクトのライフサイクル内に埋まっていることで被弾面積が広がっている

一方で追い風となる資産も確認した:

- `StateManager`（785 行）の Qt 依存は **シグナル 4 本のみ**。held/commit（「反映」）の
  二相機構も含め本体は純 Python
- `StartGGDataProvider`（2,291 行）・`AutonaApiV1`（733 行）はじめ **約 6,600 行が既に Qt-free**
- v1 API は検証・冪等性・重量操作ガード・op-log を備えた Qt 非依存の上位層として完成しており、
  REST(v1) / REST(legacy) / Socket.IO の 3 系統は Actions を唯一の下流として共有している
  （= Actions を差し替えれば 3 系統が同時に追随する）
- 初期シードは `_SeedBoardState` / `_SeedPanelState` として既に部分的にウィジェット外へ抽出済み
- 本方針は Design.md R-Sync-1 ⑤・T-18（M4）として既に予告されており、
  M4 は「PR 前に追加 Design ドキュメントを書く」ことを条件としている（本 ADR + 設計書がそれ）

また ROADMAP の Tier 2（`/dashboard`・`/caster-view`・複数オペレーター分業）は
「Web からの全操作」を前提とするため、Qt ウィジェットが書き込み主体である限り実現できない。

## Decision

### D1: 状態とドメインロジックの正本を Headless Core（Qt import ゼロ）に置く

`StateManager`・新設 `AutonaActions`（ドメイン操作）・state スキーマ定義（キーパスカタログ、
held/exempt 定義、シード）を Qt 非依存の core 層とし、**core の Qt import ゼロをテストで恒久固定**する
（`test_import_side_effects.py` と同じ subprocess pin 方式）。`StateManager` の Qt シグナル 4 本は
汎用 observer に置換し、Qt への通知はアダプタ（StateManagerBridge）が担う。

### D2: すべての書き込み経路を Actions 一本に集約し、Qt を「クライアントの一つ」に降格する

Qt ウィジェットのハンドラ・REST(v1/legacy)・Socket.IO・グローバルホットキーは、
いずれも `AutonaActions` を呼ぶ。ウィジェットは「表示 + 操作を Actions に依頼する」役割に限定し、
`StateManager.Set` の直接呼び出しを段階的にゼロにする（R-Sync-1 ③の暫定許可を撤廃）。
ドメインロジック（セットデータ正規化・統計集計・ステージトラッキング・クルー合計計算等）は
ウィジェットから core へ抽出する。

### D3: スキーマの正本を core に移し、`objectName` 依存キーパスを静的化する（T-19 統合）

キーパスのカタログを core に定義し、ウィジェットは「objectName = キー」の暗黙結合ではなく
カタログを参照する。保存データ互換はマイグレーション層で守る。これは T-18 と不可分であり、
Actions 化だけ行ってもウィジェット構造がスキーマの正本であり続けるため、セットで計画する。

### D4: 一撃の作り直しはせず、独立リリース可能なステップで段階移行する

ADR-003 D3 と同じ規律（1 PR = 独立検証・revert 可能、二分探索できる履歴）を踏襲する。
移行順序は「リスク昇順」: 掃除 → core 境界確立 → シード/スキーマ移動 → ホットキー付け替え →
データロード系抽出 → UI 直接反応の移行（最難関・最後）。移行期間中は新旧経路が併存するが、
各ステップで「この操作は Actions 経由に移行済み」を明示的に線引きする。

## Alternatives considered

- **(A) 現状維持 + 運用ルール強化（新規実装のみ Actions 経由）**:
  既存 197 箇所と 4 経路併存はそのまま残り、「パネル未構築で書き込みが死ぬ」構造も
  ROADMAP Tier 2 との矛盾も解消しない。R-Sync-1 ⑤を無期限先送りするだけ。→ 不採用。
- **(B) フル書き直し / スタック変更（Web アプリ化・Tauri 等）**:
  Qt 地雷は消えるが、グローバルホットキー・WebEngine 画像生成・自動更新・ローカル資産管理を
  含むデスクトップ機能の全再実装となり、5 ヶ月分の実地知識（更新ヘルパーの失敗モード、
  Start.gg API の限界値、OBS 挙動）を再学習するコストが機能開発を半年以上停止させる。
  配布中のプロダクト（v1.7.x・自動更新ユーザーあり）に対して正当化できない。→ 不採用
  （ADR-003 が一括書き直しを不採用にしたのと同じ理由）。
- **(C) core の別プロセス常駐（デーモン化・エンジン分離）**:
  「軽く・堅牢」に一見適合するが、IPC 層・プロセスライフサイクル管理・認証が新規の
  複雑性として乗る。in-process の層分離でもテスト可能性と書き込み一元化は同等に得られる。
  複数マシン・複数オペレーター運用が実要件になった時点で再検討する。→ 現段階では不採用
  （Revisit conditions 参照）。

## Consequences

**良い影響:**

- 書き込み経路が 1 本になり、「パネル未構築で操作が無言で死ぬ」「経路ごとに挙動が違う」
  クラスのバグが構造的に消える。ホットキーもパネルの生死と無関係に動く
- core が QApplication なしでテスト可能になり、現在カバレッジゼロの中核ロジック
  （過去バグ最多の「UI⇄State 同期」領域）に高速な単体テストを書ける
- ドメインロジックが Qt オブジェクトのライフサイクル（Shiboken wrapper 地雷群）から隔離され、
  ネイティブクラッシュの被弾面積が縮小する
- ROADMAP Tier 2（Web ダッシュボード・複数オペレーター）への前提条件が整う
- スキーマが明文化され、`.ui` の objectName 変更が保存データを壊す結合（S-14）が解消に向かう

**受け入れるリスク・コスト:**

- Actions の headless 化は「移設」ではなく**ウィジェットからのロジック書き起こし**がほぼ全量
  （既存 Actions はリモコンであり、中身が存在しない）。最大工数は (a) UI 直接反応 197 箇所の移行
- 移行期間中の新旧経路併存。エコーループ（Actions が書いた state 変更をウィジェットが受けて
  再度書き戻す）への抑止設計が各ステップで必要
- キーパス静的化は保存データ互換に触れる。マイグレーション層の新設が前提
- 「軽さ」への直接効果は限定的（WebEngine はプレビュー 4 パネル + Designer が使い続ける）。
  軽量化は未使用依存の削除・遅延構築の徹底・core の起動独立性向上という形で実現する

**非目標（本 ADR では変えないもの）:**

- 技術スタック（Python + PySide6 + Flask/Socket.IO + React）
- legacy REST / Socket.IO の外部契約（44 ルート + 39 イベントの台帳は維持）
- OBS オーバーレイのレイアウト方式・`out/` ファイル出力
- LAN 公開時の認証（現状の loopback 既定 + opt-in を維持。認証設計は core の
  プロセス分離・リモート運用を採る場合の前提条件として別 ADR で扱う）

## Revisit conditions

- 複数マシン・複数オペレーターの同時運用が実要件になった場合、(C) プロセス分離 + 認証を
  別 ADR として再検討する（本 ADR の層分離はその準備段階を兼ねる）
- マイグレーション層で保存データ互換を守れないキーが出た場合、`STATE_VERSION` による
  一括変換方式へ切り替える
- 移行ステップ中にネイティブクラッシュ・回帰が頻発した場合、ADR-003 と同様に
  粒度をさらに細分化する（1 PR = 1 ウィジェット → 1 PR = 1 操作グループ）
