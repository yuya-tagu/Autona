# ADR-003: 起動アーキテクチャ（単一インスタンス + 明示的ライフサイクル）

## Status

Accepted（2026-07-28・PdM 方針承認。各移行ステップの着手は個別指示による）

> 設計詳細・移行ステップ・検証方法は
> [../changes/startup-architecture-redesign.md](../changes/startup-architecture-redesign.md) を正とする。
> 本 ADR は「なぜこの方針か」の記録のみを持つ。

## Context

「起動が遅い（ウィンドウ表示まで実測 22〜23 秒）」「exe 連続起動で多重起動する」という
2 つの実害が報告された。2026-07-28 の調査（コード静的解析 + 過去起動ログの実測）で、
両者は同一の構造要因に帰着することを確認した:

- 単一インスタンスガードが存在しない（リポジトリ全域で確認）
- `import src` 完了までスプラッシュを含め何も描画されない（無反応区間 → 連打 → 多重起動）
- module import の副作用でシングルトンが生成され、**import 順序 = 初期化順序**になっている
  （[.claude/rules/agent-pitfalls.md](../../.claude/rules/agent-pitfalls.md) #1・#2 はこの設計の症状）
- `Window.__init__` が全パネル・全ウィンドウ・WebEngine ×6・選手 DB 2937 件を同期構築する

また Autona はポート・`out/` 状態ファイル・グローバルホットキー・OBS オーバーレイという
**排他的グローバル資源を占有する**アプリであり、多重起動は「壊れる」以前に意味を成さない。

## Decision

### D1: 単一インスタンスを仕様として明文化する

2 回目の起動は「既存ウィンドウの前面化 + 即終了」とする（OBS / DAW と同じ挙動）。
実装は named mutex（`import src` 前の軽量ゲート）+ QLocalServer による前面化ハンドオフ。
これはパッチではなく、アプリの本質（排他資源の占有）の表現である。

### D2: import 副作用を全廃し、明示的ブートストラップ（composition root）へ移行する

どの src モジュールを import しても副作用ゼロ。シングルトン生成順は `src/bootstrap.py` が
1 箇所で明示する。「4 段起動（ガード → フィードバック → 最小コア → 遅延初期化）」は
この構造から導かれる帰結であり、並べ替えを目標としない。

### D3: 一撃の作り直しはせず、独立リリース可能なステップで段階移行する

シングルトン初期化順序は本リポジトリ最大の地雷原（C++ クラッシュ実績複数）のため、
1 PR = 1〜2 シングルトンの粒度・毎ステップ検証・revert 可能な履歴を厳守する。
ステップ定義と検証チェックリストは設計書（changes/）を正とする。

## Alternatives considered

- **(A) 現行構造のまま起動 4 段化（初期化順の並べ替え + 個別遅延）**:
  import した瞬間に生成されるものは遅延できず、import 1 行の追加で段構造が静かに崩れる。
  強制する仕組みがなく、将来の機能追加で再び起動が遅くなる。→ 不採用（不十分）。
- **(B) 一括フル書き直し**: 影響範囲が `Autona.py` 全域 + 全シングルトンに及び、
  初期化順序の地雷を一度に踏む。二分探索できない巨大変更は本リポジトリの実績上危険。→ 不採用。
- **(C) 多重起動ガードのみ追加（最小対処）**: 実害の一つは止まるが「無反応 → 連打」の
  動機と起動 22 秒は残る。根本要因（import 副作用）に触れない。→ 単独では不採用
  （採用案の Step 1 として包含）。

## Consequences

**良い影響:**
- 多重起動が構造的に不可能になり、ポート競合・状態ファイル後勝ち上書き・誤 kill が消滅
- 初期化順序が bootstrap 上で可視化され、agent-pitfalls #1・#2 が構造ごと消滅
  （テストの `direct_import()` 回避策も不要になる）
- パネルの lazy 化が一貫して可能になり、起動時間が「機能数に比例して伸びる」構造から脱却

**受け入れるリスク・コスト:**
- QApplication 生成位置の移動は全 Qt オブジェクトの前提に関わる（QtWebEngine の
  初期化順制約を dev / frozen 両方で検証必須）
- 移行期間中、シングルトンの暗黙依存が顕在化してクラッシュしうる（粒度厳守で局所化する）
- WebServer を表示後起動に遅らせるため、OBS ブラウザソースの取得開始が数秒遅れる
  （2026-07-28 PdM 承認済み・配信運用上許容）

## Revisit conditions

- Step 1（ガード + 早期フィードバック）実施後に多重起動・連打の実害が解消した場合、
  Step 3 以降の優先度を他の機能開発と比較して再判断する
- QtWebEngine の初期化順制約が frozen 環境で解決できない場合、Stage 1 の実現方式
  （スプラッシュの出し方）を再検討する
- マルチインスタンスの正当な用途（例: 別大会を同時運用）が将来要望された場合、
  D1 を「プロファイル分離（ポート・出力先の分離）」として再設計する
