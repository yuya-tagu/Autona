# オーケストレータ運用

メインセッションを 1 本だけ常時稼働させ、オーケストレータとして機能させる運用。
Hivee の運用（`30_Products/Hivee/.claude/orchestration.md`）を Autona 向けに移植したもの。

## 基本形

- **メインセッションは常に 1 本**。複数の対話セッションで同じ作業ツリーを並行編集しない
  （`git status` の混合・push 時の巻き込みが起きるため）
- **メインはタスク分解・委譲・検収・PR 作成・PdM との要件すり合わせに専念する**。
  自明な 1〜2 行修正を除き自分でコードを書かない
- 修正は**基本直列**: ローカル `main` 直編集 → 検証 1 回 → PR 1 本

## 委譲先の選び方

| 作業 | 委譲先 |
|------|--------|
| コード探索・横断検索・複数ファイル読み | 組み込み **Explore**（結論だけ受け取る） |
| 設計が決まっている変更（規模・ファイル数は問わない） | **patch**（Sonnet） |
| 設計判断を含む変更 / Qt ライフサイクル・スレッド境界・`bootstrap.py` 生成順・state スキーマ・自動更新に触れる変更 / 原因不明のバグ・Qt クラッシュ調査 | **impl**（Opus） |
| フル検証（pytest 全量・Web UI build/test） | **verify**（Sonnet） |
| 差分レビュー・成果物の検収・PR 前セルフレビュー | **review**（Opus） |
| 難航案件の第三者レビュー・判断が割れた差分のセカンドオピニオン・アーキテクチャ評価 | Agent 呼び出しで `model: "fable"` を上書き（review か general-purpose） |

- **振り分けは「設計が決まっているか」で決める（規模では決めない）**。設計確定済みなら大量の機械的変更でも patch
- 設計を詰める段階（方針・境界・移行順序）はメインが行い、決まった設計を patch / impl に渡す
- 委譲の brief には「目的・読むべきファイル・完了条件・触ってはいけないファイル（他作業の未コミット変更）」を必ず書く

## 標準フロー（1 タスク）

1. **分解**: 台帳（下記）から次のタスクを取り、設計判断が要るかを決める
2. **実装**: patch / impl に委譲。独立した部分は並列起動してよい（触るファイルが重ならない場合のみ）
3. **検収**: 差分が中規模以上、または Qt ライフサイクル・スレッド・state に触れたら **review** に回す。
   指摘はメインが取捨選択し、直すものは元の実装エージェント（SendMessage で継続）か patch に戻す
4. **検証**: push 前に **verify** でフル検証（pytest 全量 + `web/` 変更時は build/test）
5. **PR**: オーナーに依頼されたら、メインがコミット → push → `gh pr create`（CLAUDE.local.md の認証手順）。コミット・push を依頼なしに行わない
6. **台帳更新**: 進捗を台帳に書く

メインが自分で読むのは、サブエージェントの報告・`git diff --stat`・要所の数行だけにする。
テストログやファイル本文の通読はサブエージェントに任せる。

## 動作確認の分担

- **pytest はエージェントが回す**。impl / patch は影響範囲のテストだけ、全量は verify が回す
- **`python main.py` / exe の起動・GUI 操作はエージェントもメインもしない**。実機確認はオーナーが行い、
  PR の Test Plan に未チェックで明記する
- exe ビルドは明示指示があるときだけメインで実行する

## モデル運用

- **メインは Opus**。Fable はメインや通常の委譲先には使わず、上表の第三者レビュー用途に限る
- サブエージェントのモデル・effort は各 frontmatter が正本。格上げ・格下げは Agent 呼び出しの
  `model` / `effort` 上書きで行ってよい
- effort はモデル世代ごとに意味が変わる。モデル更新時は値を持ち越さず、impl の所要時間と検収 NG 率で較正する
- メインのモデル切替はセッション途中で行わず、compact 区切りで行う

## 状態の正本はディスク（compact 耐性）

進行状態をコンテキストに置かない。台帳を読んで着手し、終わったら台帳を更新する。

| 台帳 | 内容 |
|------|------|
| [../docs/changes/architecture-modernization.md](../docs/changes/architecture-modernization.md) §4.4 / §5 | ADR-005 移行ステップ（S0〜S-final）と実施記録 |
| [known-smells.md](known-smells.md) | リファクタ候補 |
| [manual-test-checklist.md](manual-test-checklist.md) | オーナーに依頼する手動確認項目 |

### 区切りルーチン（PR マージごと）

1. **書き切る**: 台帳の更新と、PdM 判断待ち論点をディスクへ反映する
2. **同期する**: `main` を origin に ff 同期する（CLAUDE.local.md の fetch 手順）
3. **宣言する**: メインが「compact 区切りです」と PdM へ促す（`/compact` はユーザーコマンド）
4. **復元する**: compact 後の最初のターンで台帳を読み直し、次タスクへ

auto-compact の閾値は [settings.json](settings.json) の `autoCompactWindow`（400k）。
区切り前に自動発動したら、メインで物量作業をしている兆候として委譲不足を疑う。

## 並列作業（worktree サブエージェント）

ローカル worktree は通常使わない（CLAUDE.md の Git ルール）。例外として、独立した修正が複数溜まったときだけ
`patch` / `impl` を `isolation: "worktree"` で並行起動してよい。**以下をすべて満たすものに限る**:

1. 修正同士が独立している（同一ファイルに触れない）
2. `layout/` の実行時生成物・`user_data/`・`out/` に依存するテストを含まない
   （worktree には未追跡のローカルデータが無い）
3. state スキーマ・保存データ形式・自動更新に触れない
4. `web/` を触らない（worktree には `web/node_modules` が無く、build/test と jsdom 系テストが回らない）

**還流手順（置き去り禁止）**: 完了後に worktree の diff をメインツリーの `main` へ適用 → worktree を削除 →
メインツリーで verify を回してから PR フローへ。

## Remote Control

- リモートからの指示は**バックログ追加・優先順位変更・検収 OK/NG 判断**に寄せる
- **push / PR 作成 / リリース操作は明示依頼時のみ**（外から触れても不可逆操作の規律は下げない）
