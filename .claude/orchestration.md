# オーケストレータ運用

メインセッションを 1 本だけ常時稼働させ、オーケストレータとして機能させる運用。
Hivee の運用（`30_Products/Hivee/.claude/orchestration.md`）を Autona 向けに移植したもの。

## 基本形

- **メインセッションは常に 1 本**。複数の対話セッションで同じ作業ツリーを並行編集しない
  （`git status` の混合・push 時の巻き込みが起きるため）
- **メインはタスク分解・委譲・検収・PR 作成・PdM との要件すり合わせに専念する**。
  自分でコードを書くのは次の場合だけ（2026-11-17 オーナー指示。委譲は文脈の読み直しから始まるので、小さい変更では遅い）:
  - 自明な 1〜2 行修正
  - **調査済みの小さい変更**: 直す場所と直し方がメインの手元で分かっていて、1 ページ（`web/src/<Page>/`）か 1 モジュールとそのテストに収まり、
    設計判断が無いもの（欄の増減・文言・配置・既存パターンどおりの 1 フィールド追加など）
  - 上に当てはまっても、Qt ライフサイクル・スレッド境界・`bootstrap.py` の生成順・state スキーマ・自動更新に触れるなら委譲する（impl）。
    書いている途中で範囲が広がったら、そこで止めて委譲に切り替える
- 修正は**基本直列**: ローカル `main` 直編集 → 検証 1 回 → PR 1 本

## 委譲先の選び方

| 作業 | 委譲先 |
|------|--------|
| コード探索・横断検索・複数ファイル読み | 組み込み **Explore**（結論だけ受け取る） |
| 設計が決まっている変更（規模・ファイル数は問わない） | **patch**（Sonnet） |
| 設計判断を含む変更 / Qt ライフサイクル・スレッド境界・`bootstrap.py` 生成順・state スキーマ・自動更新に触れる変更 / 原因不明のバグ・Qt クラッシュ調査 | **impl**（Opus） |
| フル検証（pytest 全量・Web UI build/test） | **verify**（Haiku） |
| 差分レビュー・成果物の検収・PR 前セルフレビュー | **review**（Opus） |
| 難航案件の第三者レビュー・判断が割れた差分のセカンドオピニオン・アーキテクチャ評価 | Agent 呼び出しで `model: "fable"` を上書き（review か general-purpose） |

- **Haiku で足りる作業は Haiku に寄せる**: 判断を伴わない実行・集計（verify）と探索（Explore）は Haiku。コードを書く patch は agent-pitfalls を踏まえる必要があるので Sonnet のまま
- **振り分けは「設計が決まっているか」で決める（規模では決めない）**。設計確定済みなら大量の機械的変更でも patch
- 設計を詰める段階（方針・境界・移行順序）はメインが行い、決まった設計を patch / impl に渡す
- 委譲の brief には「目的・読むべきファイル・完了条件・触ってはいけないファイル（他作業の未コミット変更）」を必ず書く

## 標準フロー（1 タスク）

1. **分解**: 台帳（下記）から次のタスクを取り、設計判断が要るかを決める
2. **実装**: patch / impl に委譲（基本形の「調査済みの小さい変更」はメインが書く）。独立した部分は並列起動してよい（触るファイルが重ならない場合のみ）
   - **画面の変更は UI を先に出して見せる**（2026-11-17 オーナー指示）: 欄の配置など目で判断するものは、UI だけを先に直してオーナーに見せ、
     サーバー側（core・v1・ドキュメント）は続けて足す。UI・API・core・テスト・ドキュメントを 1 つの依頼にまとめて、画面を見せるのを最後にしない
3. **検収**: 差分が中規模以上、または Qt ライフサイクル・スレッド・state に触れたら **review** に回す。
   指摘はメインが取捨選択し、直すものは元の実装エージェント（SendMessage で継続）か patch に戻す
4. **検証**: 影響範囲のテストを実施する。大規模な修正の場合は最後に **verify** でフル検証（pytest 全量 + `web/` 変更時は build/test）。範囲の決め方は下記「テストの範囲」
5. **実機確認**: メインが隔離データで行う（下記「動作確認の分担」）。画面に影響しない変更では省く
6. **PR**: オーナーに依頼されたら、メインがコミット → push → `gh pr create`（CLAUDE.local.md の認証手順）。コミット・push を依頼なしに行わない。ADR-005 のパネル移行は 2026-11-07 から依頼済みとして扱う
7. **台帳更新**: 進捗を台帳に書く

メインが自分で読むのは、サブエージェントの報告・`git diff --stat`・要所の数行だけにする。
テストログやファイル本文の通読はサブエージェントに任せる。

## 動作確認の分担

- **pytest はエージェントが回す**。impl / patch は影響範囲のテストだけ、全量は verify が `python scripts/run_tests_parallel.py`（並列・約 3〜6 分、マシンの状態で変動。CI は直列のまま）で回す
- **テストの範囲**（2026-11-17 オーナー指示）: **影響範囲のテストを実施する。大規模な修正の場合は最後に全量チェックする**。
  委譲の brief に一律で「最後に pytest 全量」と書かない
  - 影響範囲は「触ったモジュールのテスト」だけではない。この repo は横断の台帳・pin テストが変更箇所から離れたところで落ちるので、
    変更の種類に応じて次も含める:

    | 変更の種類 | 含める台帳・pin テスト |
    |-----------|----------------------|
    | ルート / Socket.IO イベントの増減、v1 のフィールドの増減 | `tests/test_webserver_routes.py`・`tests/test_web_access.py`・API 一覧（`core/ApiCatalog`）の pin |
    | state のキー・書き手・書き込み列の変更 | `tests/test_state_schema.py`・`tests/test_objectname_keypath_contract.py`・書き込み列の golden（`tests/test_board_operations.py`・`tests/test_set_follow_flow.py`・`tests/test_player_apply.py` ほか該当するもの） |
    | core の import・シングルトン・購読者の追加 | `tests/test_core_qt_free.py`・`tests/test_import_side_effects.py`・`tests/test_bootstrap_split.py` |
    | Qt のウィジェット・シグナルの接続 | `tests/test_web_panel_host.py`・`tests/test_signal_lifetime.py` |
    | `web/` | 該当ページの jest と `npm run build`（Python と表を共有する `*.cases.json` を触ったら読む側の pytest も） |
  - 「大規模」は影響範囲を列挙し切れない変更: `bootstrap.py` の生成順・state スキーマと移行・スレッド境界・横断的な rename・
    多数のモジュールにまたがる変更
  - 漏れた分は PR の CI（全量・緑でないとマージされない）が拾う。失うのは push 前に気づけることだけ
  - **push・PR の前だからという理由で全量を回さない**。「PR を出して」で足すのは review（区分「通常」以上）だけで、テストは実装時に
    通した影響範囲のものが検証になる（2026-11-18、区分「通常」のアーカイブの PR 前に verify を起動してオーナーに止められた。
    原因は verify の説明文が「push 前のフル検証」だったことと、PR の手順（git-workflow.md）だけを読んでこの節を読み直さなかったこと）
- **実機確認はメインセッションが PR の前に行う**（2026-11-07 オーナー承認）。サブエージェントはアプリを起動しない
  - **隔離データでだけ起動する**: tmp の作業ディレクトリ・空きポート・専用の `AUTONA_INSTANCE_TAG`。
    開発者の作業ディレクトリでアプリ本体（デスクトップ版 / exe / ヘッドレス）を起動しない。
    本物の `user_data` と選手 DB を使わず、検証データは仮のものにする
  - 終わったら起動したプロセスだけを止める。オーナーが起動した Autona には触らない
  - 同じ確認で 3〜4 回失敗したら手法を変えるか、その項目を未確認にして進む
    （2026-07 に画面操作を繰り返して成果が出なかった経緯がある）
  - 確認できなかった項目は PR の Test Plan に未チェックで残し、報告にも書く。OBS と配信の見た目はオーナーの確認に残す
- 隔離ディレクトリでヘッドレスを起動するテスト（`tests/test_headless_smoke.py` などのスモーク・`cd web && npm run test:e2e`）は
  サブエージェントも実行してよい
- exe ビルドは明示指示があるときだけメインで実行する
- **パネルの設計**: 既存の方針に沿うものはメインが決め、理由を台帳に残して進める。機能を削る、挙動を大きく変えるものだけオーナーに確認する
- **止まる条件**: 確認できない項目が製品の重要な動作に関わるとき、原因の分からない失敗が出たときは、マージせずに止まって報告する

## モデル運用

- **メインは Opus（常に fast mode）**。`.claude/settings.json` の `"fastMode": true` で既定オンにしている（Sonnet / Haiku は fast mode 非対応で影響なし。サブエージェントの impl / review（opus）へ fast mode が伝播するかは公式に未記載）。Fable はメインや通常の委譲先には使わず、上表の第三者レビュー用途に限る
- サブエージェントのモデル・effort は各 frontmatter が正本。格上げ・格下げは Agent 呼び出しの
  `model` / `effort` 上書きで行ってよい
- effort はモデル世代ごとに意味が変わる。モデル更新時は値を持ち越さず、impl の所要時間と検収 NG 率で較正する
- メインのモデル切替はセッション途中で行わず、compact 区切りで行う

## 状態の正本はディスク（compact 耐性）

進行状態をコンテキストに置かない。台帳を読んで着手し、終わったら台帳を更新する。

| 台帳 | 内容 |
|------|------|
| [../docs/changes/architecture-modernization.md](../docs/changes/architecture-modernization.md) §4.4 / §5 | ADR-005 移行ステップ（S0〜S-final）と実施記録 |
| [known-smells.md](known-smells.md) | リファクタ候補 |
| [manual-test-checklist.md](manual-test-checklist.md) | 手動確認項目（メインの実機確認と、オーナーに残す項目） |

### 区切りルーチン（PR マージごと）

1. **書き切る**: 台帳の更新と、PdM 判断待ち論点をディスクへ反映する
2. **同期する**: `main` を origin に ff 同期する（CLAUDE.local.md の fetch 手順）
3. **宣言する**: メインが「compact 区切りです」と PdM へ促す（`/compact` はユーザーコマンド）
4. **復元する**: compact 後の最初のターンで台帳を読み直し、次タスクへ

auto-compact の閾値は [settings.json](settings.json) の `autoCompactWindow`（400k）。
区切り前に自動発動したら、メインで物量作業をしている兆候として委譲不足を疑う。

## 並列作業（worktree サブエージェント）

ローカル worktree は通常使わない（CLAUDE.md の Git ルール）。例外として、独立した修正が複数溜まったときだけ
`patch` / `impl` を `isolation: "worktree"` で並行起動してよい。**以下をすべて満たすものに限る**:

1. 修正同士が独立している（同一ファイルに触れない）
2. `layout/` の実行時生成物・`user_data/`・`out/` に依存するテストを含まない
   （worktree には未追跡のローカルデータが無い）
3. state スキーマ・保存データ形式・自動更新に触れない
4. `web/` を触らない（worktree には `web/node_modules` が無く、build/test と jsdom 系テストが回らない）

**還流手順（置き去り禁止）**: 完了後に worktree の diff をメインツリーの `main` へ適用 → worktree を削除 →
メインツリーで verify を回してから PR フローへ。

## Remote Control

- リモートからの指示は**バックログ追加・優先順位変更・検収 OK/NG 判断**に寄せる
- **push / PR 作成 / リリース操作は明示依頼時のみ**（外から触れても不可逆操作の規律は下げない）
